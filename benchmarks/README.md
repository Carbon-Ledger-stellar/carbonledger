# Performance Benchmark Data

See `docs/benchmarking.md` for the full methodology.

## Files

| File | Purpose |
|------|---------|
| `baseline.json` | **Committed** baseline. Every CI run compares against this. Update intentionally (see below). |
| `current.json`  | Generated by CI on every run (not committed). Uploaded as build artifact. |
| `history.csv`   | Committed historical trend file. One row appended per run by `run_perf_benchmarks.py`. |
| `dashboard.html`| Self-contained HTML trend chart. Generated from `history.csv` by `perf_dashboard.py`. Uploaded as CI artifact on `main` pushes. |
| `api_current.json` | Intermediate API benchmark output (not committed). |
| `db_current.json`  | Intermediate DB benchmark output (not committed). |

## What is tracked (closes #1056)

Three performance dimensions are measured on every PR:

### 1. Contract — Soroban cpu_instructions
Functions: `mint_credits`, `retire_credits`, `verify_serial_range`, `bulk_purchase`
Gate metric: `cpu_instructions` (+10% = fail)

### 2. API — HTTP response time percentiles
Endpoints: `GET /health`, `GET /projects`, `GET /marketplace/listings`,
           `POST /marketplace/purchase`, `GET /audit/credits/:id/events`
Gate metric: `p95_ms` (+10% = fail)

### 3. DB — Query execution time percentiles
Queries: `projects_list_query`, `marketplace_listings_query`,
         `audit_events_query`, `retirement_lookup_query`
Gate metric: `p95_ms` (+10% = fail). Measured via `EXPLAIN ANALYZE` if
`DATABASE_URL` is available; otherwise measured as API round-trip proxy.

## Running locally

```bash
# Full benchmark (contract + API + DB) against localhost:
python3 scripts/run_perf_benchmarks.py --run

# API + DB only (no Rust toolchain needed):
python3 scripts/run_perf_benchmarks.py --run --skip-contract

# Compare-only (no new measurements):
python3 scripts/run_perf_benchmarks.py --compare-only

# Generate trend dashboard from history.csv:
python3 scripts/perf_dashboard.py
# → opens benchmarks/dashboard.html in your browser

# API benchmark only:
python3 scripts/bench_api.py --samples 50

# DB benchmark only:
DATABASE_URL=postgres://... python3 scripts/bench_db.py --samples 50
```

## CI workflow

`.github/workflows/perf-regression.yml` runs on every PR and push to `main`:

1. **`contract-benchmarks` job** — runs Soroban cargo test benchmarks, compares
   `cpu_instructions` against baseline, fails on >10% regression.
2. **`api-db-benchmarks` job** — starts PostgreSQL + Redis + NestJS backend as
   services, seeds test data, benchmarks API endpoints and DB queries, fails on
   >10% regression in any p95 metric.
3. **`history-artifact` job** — on `main` pushes only: downloads the run's
   `current.json`, appends to `history.csv`, generates `dashboard.html`, uploads
   everything as a 365-day artifact.

Regression reports are posted to the GitHub Actions job summary.

## Updating the baseline

`benchmarks/baseline.json` is intentionally **not** auto-updated by CI.
Resource-usage changes should be reviewed like any other code change.

When a PR intentionally changes a metric (optimisation, new feature, etc.):

1. Run `python3 scripts/run_perf_benchmarks.py --run` locally, or download
   `benchmarks/current.json` from the PR's CI artifact.
2. Replace `benchmarks/baseline.json` with the new numbers.
3. Append a row to `benchmarks/history.csv` with a note referencing the PR.
4. Commit both files in the same PR.

## Historical trend data

`benchmarks/history.csv` uses this schema:

| Column | Content |
|--------|---------|
| `date` | ISO date of the run (YYYY-MM-DD) |
| `function` | Metric name (function / endpoint / query key) |
| `cpu_instructions` | Contract: cpu_insns. API/DB: p95_ms value. |
| `mem_bytes` | Contract: mem_bytes. API: p50_ms. DB: p50_ms. |
| `reads` | Contract: reads. API/DB: p99_ms. |
| `writes` | Contract: writes. |
| `note` | Dimension prefix + git SHA + branch. |

Plot with `scripts/perf_dashboard.py` or any spreadsheet / pandas tool.

## Regression threshold

10%, applied to:
- Contract: `cpu_instructions` (the binding Soroban resource)
- API: `p95_ms` (the practical latency SLO metric)
- DB: `p95_ms` (direct EXPLAIN ANALYZE or API proxy)

`reads`/`writes` are reported for visibility but not part of the automated gate.
